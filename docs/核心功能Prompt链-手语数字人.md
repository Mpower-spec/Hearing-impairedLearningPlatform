## 一、先明确“数字人”到底是什么

关键取决于你已有的手语词元库格式：

| 词元库格式 | 推荐实现 |
|---|---|
| 每个词元是视频片段 | 拼接视频片段，外围用数字人皮肤或播放器包装 |
| 每个词元是骨骼动画 | 使用 Three.js/Babylon.js 加载 3D 人物，按时间线播放动作 |
| 每个词元只有 gloss 文本 | 还需要补录动作视频或骨骼数据，否则无法真正生成动作 |
| 有整句手语视频 | 优先整句检索，效果通常远好于逐词拼接 |

如果词元库是视频片段，第一版不建议强行做 3D 骨骼生成。用“分段视频 + 数字人展示界面”更稳定，视觉上也更容易做得漂亮。

## 二、整体流程

### 1. 生成结构化备课内容

当前 AI 返回的是 Markdown，不适合直接做手语匹配。

需要先把备课资料整理成结构化内容：

- 章节
- 段落
- 句子
- 关键词
- 句子语义
- 预计讲解顺序

例如“教学目标”里的每一条，都对应一个可独立讲解的句子。

### 2. 中文文本预处理

对每个句子进行：

- 标点切句
- 中文分词
- 同义词归一化
- 去除无意义语气词
- 识别专有名词、数字和英文缩写
- 判断疑问句、否定句和强调句

Java 后端可以使用 HanLP 或类似中文分词工具，不建议只靠 LLM 自由发挥。

### 3. 词元库匹配

匹配顺序建议如下：

1. 整句匹配：优先命中完整手语句子
2. 短语匹配：命中“光合作用”“细胞结构”等固定表达
3. 词元匹配：使用词元的中文名、同义词、别名匹配
4. 语义候选：由 LLM 从已有词元候选中选择一个
5. 未命中处理：进入教师人工补配

匹配结果必须包含：

- 命中的手语词元 ID
- 词元中文含义
- 置信度
- 是否为同义词
- 是否需要人工确认
- 未匹配词

LLM 只能从已有词元 ID 中选择，**不能让 LLM 自己创造词元 ID**。返回结果还需要后端逐项校验是否存在。

### 4. 手语语序整理

不能直接按中文词序拼接。

需要增加一层手语语序规则，例如：

- 时间信息前置
- 主题先行
- 核心动作和对象关系明确
- 疑问词、否定表达按手语习惯调整
- 保留必要的表情和停顿

第一版建议使用规则 + 人工审核，不要完全依赖大模型自动生成手语语法。

### 5. 生成可播放时间线

每个词元需要包含：

- 媒体地址或骨骼动画 ID
- 动作起止时间
- 持续时间
- 过渡时间
- 是否需要表情
- 是否需要强调
- 对应中文字幕

最终生成一条“手语讲解时间线”，按句子和词元顺序播放。

### 6. 教师审核

教师端需要看到：

- 原始句子
- 匹配出的手语词元
- 每个词元的置信度
- 未匹配词
- 可替换词元
- 预览视频
- 保存、重新生成、发布按钮

教师必须可以手动：

- 替换词元
- 删除词元
- 调整顺序
- 添加停顿
- 录入自定义解释
- 放弃某个句子的数字人展示，只保留字幕

### 7. 学生端播放

学生端建议展示：

- PPT
- 数字人手语画面
- 同步字幕
- 播放、暂停、慢速、逐句重播

始终保留字幕，数字人不能成为唯一信息通道。

## 三、数据库建议

不需要一开始做复杂数据库设计，但建议至少拆分以下概念。

### 手语词元表

主要字段：

- 词元 ID
- 标准 gloss
- 中文词名
- 同义词和别名
- 词元类别
- 地区或手语体系
- 媒体地址或骨骼动画 ID
- 动作起止时间
- 持续时间
- 是否包含表情动作
- 审核状态
- 版本号

### 备课手语讲稿表

主要字段：

- 课程 ID
- 备课资料 ID
- 讲稿版本
- 状态：草稿、待审核、已发布
- 总时长
- 创建教师
- 审核教师

### 讲稿句子表

主要字段：

- 所属讲稿
- 句子顺序
- 原始中文
- 手语 gloss 序列
- 匹配词元列表
- 置信度
- 人工修改标记
- 未匹配词
- 开始时间和结束时间

这样可以保留版本，不会因为重新生成一次 AI 资料就把教师修改过的内容全部覆盖。

## 五、数字人实现选择

### 方案 A：视频片段拼接

适合你已经有手语视频词元库的情况。

优点：

- 真实度高
- 实现快
- 不需要训练动作生成模型
- 适合比赛现场演示

缺点：

- 词元之间过渡可能生硬
- 面部表情和身体姿态不连续
- 需要处理好片段起止点和转场

建议使用短语级片段，而不是全部按单个词拼接。

### 方案 B：3D 骨骼动画

适合你已有骨骼动作数据的情况。

可以使用 Three.js 或 Babylon.js：

- 加载 VRM/GLB 数字人
- 按时间线播放动作
- 使用动作混合减少跳变
- 保留面部骨骼和头部动作

优点：

- 更像真正的数字人
- 可以调整镜头、速度和动作过渡

缺点：

- 动作库质量决定最终效果
- 没有表情和手部细节时，手语可读性会明显下降

### 方案 C：生成式动作模型

用 AI 直接生成手语骨骼动作。

这是最前沿也最不推荐的比赛方案，因为：

- 需要大规模手语动作数据
- 需要处理手语语法、空间关系和表情
- 生成动作容易不自然
- 现场失败后很难兜底

不建议把第一版建立在这条路线上。

## 六、比“全自动数字人”更好的做法

我更推荐“**AI 手语讲稿 + 教师确认 + 片段化数字人**”。

原因：

- AI 负责整理和检索，不负责凭空创造手语
- 教师负责语义和手语正确性
- 数字人只负责播放已经审核过的内容
- 未匹配词可以明确显示，不会悄悄生成错误动作
- 比赛演示时可以稳定展示完整流程

如果追求最高质量，最好的替代方案是：

> AI 生成手语脚本和分镜，教师或手语老师录制最终视频，数字人负责预览和辅助展示。

对于听障学生，真实手语老师的表达质量通常明显高于自动生成数字人。

## 七、最小可落地版本

第一版只做一条完整链路：

1. 选择一门已有备课资料的课程
2. 点击“生成手语讲稿”
3. 系统将备课资料拆成若干句
4. 每句话从已有手语词元库中匹配词元
5. 教师查看匹配结果并手动修正
6. 生成一段 30–60 秒的数字人预览
7. 发布到学生端
8. 学生可以播放、暂停、慢速和查看同步字幕

第一版不要做：

- 实时课堂手语翻译
- 全课程自动生成
- LLM 自由生成不存在的词元
- 复杂 3D 表情生成
- 全自动手语语法翻译

最关键的原则是：

> **数字人负责展示，词元库负责内容，AI 负责辅助匹配，教师负责最终确认。**

## 但关键限制是

它更像是“厂商云端手语翻译 + 3D 数字人”的完整方案，不一定是通用的“手语词元播放器”。

2. **厂商不支持自定义词元**
   - 只能把备课文本交给它自带的翻译服务
   - 你的手语词元库无法直接驱动这个数字人
   - 最多只能做到“AI 生成文本 → 厂商翻译成手语”
   - 不能宣传为“基于我们自己的手语词元库生成”

## 集成前必须确认

- 是否有正式 SDK 文档和授权 Token
- 是否支持导入或绑定现有手语词元库
- 是否支持传入自定义词元 ID 或自定义动作序列
- 是否提供每个词元的开始、结束时间和完成事件
- 是否允许指定域名
- 是否支持本地部署或离线资源
- 动作资源、数字人模型和商用授权范围
- 远程 SDK 版本变化和网络故障时的兜底方案

## 结论

**可以作为数字人展示和手语播放层集成。**

如果你的目标是“使用现有手语词元库构建数字人”，必须先拿到厂商的**自定义词元/动作接口**；否则只能使用它自带的手语翻译，无法真正接入你的词元库。第一版建议只做一条 PoC：用一句备课资料生成手语句子，调用 SDK 播放，并验证能否获取逐词元时间轴与完成事件。

## Turn 3：那可以根据实时字幕构建课堂的手语数字人吗

### 我的 Prompt

那可以根据实时字幕构建课堂的手语数字人吗

### codex 回复

可以做，但只能定位为“**准实时手语数字人**”，不是完全同步的实时手语翻译。

## 可行性判断

实时字幕转手语数字人的链路是：

**教师语音 → ASR 实时字幕 → 完整句子缓冲 → 手语句子/词元生成 → 数字人排队播放**

字幕可以实时出现，但手语不能简单地逐字跟着字幕播放，原因是：

- 实时字幕的中间结果会不断变化，直接用于手语会产生错误语义
- 中文手语的语序和中文不同
- 手语动作通常比说话慢，容易产生播放积压
- 专业术语和未收录词元无法自动表达
- 表情、否定、疑问等非手动信息需要额外处理

因此，真正可行的是：

> **字幕先出现，手语数字人延迟几秒，按完整句子播放**

---

## 推荐的课堂实现方式

### 1. 只使用 ASR 的最终字幕

不要用 `interim` 中间结果驱动手语，只使用最终识别结果。

后端把最终字幕先放入句子缓冲，例如累积到：

- 遇到句号、问号、感叹号
- 连续静音约 1–2 秒
- 或累计到 3–5 秒语音

再生成一个完整手语句子。

### 2. 对句子做手语友好改写

原字幕不能直接逐词匹配，需要先做：

- 删除口头语和重复词
- 拆分过长句子
- 保留主谓宾和关键术语
- 把复杂表达改成简短、明确的手语句
- 标记未收录词

例如：

> 原句：植物在阳光的照射下，利用水和二氧化碳制造有机物。

可以改写为：

> 植物 / 阳光 / 水 / 二氧化碳 / 制造 / 养分

再进入手语词元库匹配。

### 3. 词元库匹配和数字人播放

每条最终字幕生成一个手语播放任务：

- 匹配手语词元
- 生成词元顺序
- 生成动作时间轴
- 加入播放队列
- 交给 `yiyu.js` 类的数字人 SDK 播放
- 使用 `onSingleSignFinished` 和 `onSentenceFinished` 回调同步字幕和队列

如果 SDK 不支持你的自定义词元库，那么只能使用它自带的手语翻译能力，不能算你自己的词元库。

### 4. 控制延迟和积压

建议设计一个有限长度队列：

- 手语播放队列最多缓存 2–3 个句子
- 延迟超过 8–10 秒时，跳过不重要的修饰句
- 术语优先、核心句优先
- 无法匹配时保留字幕，不强行生成动作
- 数字人不播放时，保留字幕作为主通道

### 5. 学生端展示

建议布局：

- 左侧或上方：PPT
- 中间：实时字幕
- 右侧：手语数字人
- 底部：暂停、慢速、重播上一句、关闭手语

字幕始终保留，数字人只是辅助通道，不能成为唯一信息来源。

## 三个可行层级

| 层级 | 做法 | 可行性 |
|---|---|---|
| 关键词手语 | 只把手语词库中的关键词播放出来 | 最高 |
| 逐句准实时手语 | 每句最终字幕生成手语，延迟约 3–8 秒 | 适合比赛 Demo |
| 连续同步手语 | 数字人与教师语音几乎同步 | 很难，需要专业流式手语模型或人工手语翻译 |

## 最推荐比赛版本

第一版不要追求完整课堂自动手语翻译，而是做：

> **每页 PPT 预生成手语讲解 + 课堂实时字幕生成关键词手语/重点句手语**

也就是：

- 备课阶段：教师审核课程手语讲稿
- 课堂阶段：学生看到实时字幕
- 手语数字人只播放已审核的重点句或关键词
- 教师讲课中未收录内容继续用字幕呈现

这样演示稳定，也能体现核心价值。

## 结论

**可以基于实时字幕构建课堂手语数字人，但必须是延迟几秒的准实时系统，而不是逐字同步。**

如果目标是比赛 Demo，建议先做“最终字幕 → 重点句手语 → 数字人队列播放”；如果要求完整课堂同步，则需要专业流式手语模型或人工手语翻译兜底。

## 2. 网站必须使用 HTTPS

生产环境建议：

```text
https://your-domain.com
```

## 3. 生产服务器反向代理

Vite 的开发代理不会在生产环境自动生效，Nginx 需要代理本项目接口：

```nginx
server {
    listen 443 ssl;
    server_name your-domain.com;

    root /var/www/hearing-platform/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /ws/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;
    }
}
```

```text
img-src 'self' data: blob: https://avatar.gbqr.net;
```
